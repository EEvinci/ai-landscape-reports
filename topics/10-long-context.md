# Long Context（长上下文窗口）技术研究报告

> 研究范围：2024-2025 年大模型长上下文技术演进、核心技术挑战、主流技术路线、海量上下文利用方案、评估方法、国产模型横向对比及应用场景分析。
> 整理时间：2025 年

---

## 一、2024-2025 年长上下文技术突破

### 1.1 上下文窗口的军备竞赛

2023 年至 2025 年初，全球大模型厂商围绕上下文窗口长度展开了一场激烈的"军备竞赛"，窗口长度以惊人的速度扩张：从最初 GPT-4 的 8K，到 Claude 的 200K，再到 Google Gemini 的百万级 token，两年内上下文窗口扩大了超过 **100 倍**。

这一轮突破的里程碑事件包括：

| 模型 | 厂商 | 上下文窗口 | 标志性意义 |
|------|------|-----------|-----------|
| GPT-4 Turbo | OpenAI | 128K tokens | 2023年末，商业模型正式进入"超长上下文"时代 |
| Claude 3 (Sonnet/Haiku) | Anthropic | 200K tokens | 2024年初，以稳定性和准确性著称 |
| **Gemini 1.5 Pro** | Google | **1M tokens**（约70万汉字） | 2024年5月，率先突破百万级，引发行业震动 |
| **Kimi** | 月之暗面 | 200K tokens | 2024年初，国内首款以"超长上下文"为核心卖点的大模型产品 |
| Claude 3.5 Sonnet | Anthropic | 200K tokens | 2024年中，代码和推理能力大幅提升 |
| GPT-4o | OpenAI | 128K tokens | 2024年5月，多模态+长上下文的统一 |
| **Llama 4 Scout** | Meta | **10M tokens** | 2025年，开源模型首次突破千万级 |

Google Gemini 1.5 的百万 token 上下文尤其值得深入分析。1M token 约等于：
- 50 集电视剧的完整字幕
- 一部《战争与和平》长度的文学作品（约 58 万词）
- 5-7 份完整年报的叠加

这种能力使 Gemini 能够执行此前完全不可能的任务，例如一次性分析一整年的公司所有邮件记录、或同时研读数百篇学术论文并提炼跨领域结论。

### 1.2 突破背后的驱动力

长上下文窗口的快速扩张并非单纯的技术炫技，而是源于三类真实需求的强力驱动：

**复杂任务的端到端处理。** 金融分析、法律合规审查、代码库理解等场景，涉及对大量相关文档的整体理解，传统的 RAG（检索增强生成）方案在处理跨文档关联推理时存在天然缺陷：检索返回的片段是孤立的，无法建模文档之间的关系。长上下文模型可以直接持有完整文档集，让模型自主发现关联。

**Agent 系统的大规模状态维护。** 多步骤 Agent 任务需要模型在整个对话周期内维护完整的状态历史，包括：工具调用的参数与结果、中间推理步骤、用户提供的额外上下文。当任务复杂度增加时，短上下文导致的状态截断（truncation）成为 Agent 失败的主要原因之一。

**RAG 与上下文的互补与竞争。** 有趣的是，长上下文与 RAG 正在形成互补而非替代关系：在超过模型有效上下文上限（如 1M token 之后）的场景中，RAG 仍然是必要的；但在 1M token 以内，长上下文正在逐步取代 RAG，减少了对向量检索系统的依赖。

## 二、核心技术挑战

### 2.1 注意力机制的二次复杂度

Transformer 的核心注意力计算复杂度为 **O(n²)**，其中 n 为序列长度。这一数学特性意味着：当序列长度翻倍时，计算量增加四倍。

以 LLaMA-3-8B 在 A100 GPU 上的实测数据为例：
- 30 万 Token 提示的 Prefill（前向预填充）阶段需要约 **6 分钟**
- 100 万 Token 提示的 Prefill 阶段则增至约 **30 分钟**
- 注意力计算本身占 Prefill 阶段总延迟的 **90% 以上**

更根本的问题是 KV 缓存（Key-Value Cache）的显存占用。在自回归生成中，每个已生成的 token 都需要将其 Key 和 Value 向量缓存以供后续 token 使用。对于一个 70B 参数的模型，当上下文达到 128K tokens 时，KV 缓存的显存占用可达 **16 GB 以上**，这对于多用户并发推理构成了严重的资源瓶颈。

### 2.2 位置编码外推困境

Transformer 通过位置编码（Position Encoding）赋予模型理解 token 空间位置的能力。模型在预训练阶段见过的最大位置编号，形成了其位置编码的"舒适区"。

当上下文窗口被扩展到训练长度之外时，模型会遇到位置索引的"未见区域"。标准 Transformer 的绝对位置编码在这些未见位置会产生完全无意义的数值，导致注意力分布崩溃，模型输出退化。2023 年的早期实验表明，简单地将上下文窗口外推 2-4 倍，就足以让模型性能严重下降。

"lost in the middle"（迷失在中间）是另一个典型症状：模型倾向于记住文档的开头和结尾，但对中间部分的内容记忆模糊。随着上下文越来越长，这一问题愈发突出。

### 2.3 知识遗忘与注意力分散

序列越长，注意力越容易分散。Transformer 的注意力机制会在所有 token 上计算加权和，当序列从 4K 扩展到 128K 时，每个 token 需要聚合的信息量增加了 32 倍，模型很难有效区分重要与不重要的上下文 token。

这带来两个层面的挑战：
- **知识遗忘**：早期内容的信息被后续 tokens 稀释，模型倾向于"近因偏差"（recency bias），更关注最近的 tokens。
- **关键信息定位困难**：在长序列中定位关键信息（大海捞针问题），要求模型在全文范围内进行精确的信息检索，而非简单依赖局部窗口。

## 三、技术路线全解析

### 3.1 位置编码外推：从 RoPE 到 LongRoPE

**旋转位置编码（RoPE, Rotary Position Embedding）** 是目前最主流的位置编码方案，被 LLaMA、GLM、Qwen、Mistral 等几乎所有主流开源模型采用。RoPE 通过旋转矩阵将绝对位置信息编码为 token 的表示，同时在注意力计算中自然引入相对位置关系，兼具绝对编码的实现便利性和相对编码的泛化潜力。

围绕 RoPE 的长度外推，研究社区发展出两条主要技术路线：

**路线一：限制注意力范围。** ALiBi（线性偏差注意力）对 attention score 按 token 距离施加线性或指数惩罚，强制模型不过度依赖远距离 tokens。StreamingLLM（MIT，2023 年）则通过保留前几个特殊的"锚点 token"（sink tokens）配合局部窗口，实现近乎"无限"长度的输入——但需注意，这只是一种**流式推理技巧**，它允许处理超长输入，但并不真正扩展模型对上下文的"理解窗口"。

**路线二：调整旋转角度。** 这是最核心的外推方向，包含多个里程碑式的工作：

- **Position Interpolation（PI，位置插值）**：Meta 在 LLaMA Long（2023 年）中提出，将超出训练范围的位置索引等比例缩放至训练区间内。仅需 1000 步微调，即可将 LLaMA 从 2K 扩展到 32K，奠定了微调外推的基础范式。
- **YaRN**：在 RoPE 基础上引入注意力缩放因子，通过精细调整旋转角度的频率分布——高频维度保持精细以编码局部细节，低频维度平滑插值以覆盖远距离——显著提升外推的稳定性。
- **LongRoPE（2024 年）**：采用**非均匀插值**策略，对每个 RoPE 维度和不同 token 位置分别搜索最优的旋转角度缩放因子，无需重新训练即可将上下文窗口扩展到 **2048K（200 万 token）**，是目前 RoPE 外推最激进的方法之一。

### 3.2 Ring Attention 与 Flash Attention：工程突破的双引擎

**Ring Attention**（Meta & UC Berkeley，2023 年）解决了单 GPU 无法容纳长序列注意力计算的问题。其核心思想是将长序列分块并分配到多 GPU 上并行处理，每个 GPU 计算局部注意力后，通过环形通信传递 Key/Value 矩阵进行跨设备聚合。关键特性是：上下文长度与设备数量呈**线性扩展**关系，可以理论上无限扩展。

**Flash Attention**（Stanford，2022-2024 年）则在单卡层面进行了革命性优化。传统注意力实现需要将完整的注意力矩阵（n×n）全部加载到显存（HBM）中再计算，造成大量显存读写开销。Flash Attention 通过**IO-aware 的分块矩阵运算**，将 HBM 读写次数减少数十倍，同时保持数学上完全等价的精确注意力（而非近似）。从 Flash Attention-1 到 Flash Attention-3，迭代中持续引入更激进的算法优化（如 Flash-Decoding 引入 K/V 序列长度的独立并行化维度），在 64K-256K 序列长度上实现约 **3-16 倍**的速度提升。

Flash Attention 与 Ring Attention **可正交叠加**：在多 GPU 集群上，每张卡先用 Flash Attention 加速局部计算，再通过 Ring Attention 进行跨卡聚合，这是当前训练和推理超长上下文模型的主流架构。

### 3.3 稀疏注意力：端到端可训练的新范式

传统稀疏注意力方法（如 Longformer、BigBird）在预训练完成后进行稀疏化，存在一个根本缺陷：压缩后的稀疏模式与预训练的稠密注意力轨迹不一致，导致能力退化。2025 年最具突破性的解决方案是 **DeepSeek Native Sparse Attention（NSA）**。

NSA 由 DeepSeek 团队提出（arXiv:2502.11089），核心创新是**三层并行稀疏架构**，通过硬件对齐的动态稀疏策略，同时实现了可训练性和高效率：

1. **压缩注意力（Compressed Attention）**：将每 32 个连续 token 压缩为 1 个粗粒度表示，压缩比 1/32，大幅降低长期依赖的计算量，同时通过可学习的 MLP 生成有意义的压缩表示。

2. **选择注意力（Selected Attention）**：基于压缩注意力的得分，动态选出 Top-16 最重要的块进行细粒度计算。块级选择策略符合注意力得分的空间连续性规律，硬件友好（连续内存访问）。

3. **滑动窗口注意力（Sliding Window）**：保留最近 512 个 token 的原始细粒度表示，防止模型因过度依赖压缩路径而忽略局部模式。

三路输出通过**门控机制动态加权融合**，训练时梯度可正常反向传播，这是 NSA 与之前稀疏方法最本质的区别。硬件层面采用了组中心数据加载（Group-Centric Data Loading）和 Triton 内核优化。工程实测数据：64K 序列下，**解码速度提升 11.6 倍，前向传播 9 倍，内存访问量降至 1/11**，且大海捞针测试准确率达到 100%。

### 3.4 海量上下文的智能利用

即便解决了计算效率问题，模型如何真正"利用"海量上下文仍是挑战。2024 年的研究提出了多类互补方案：

- **选择性复制（Selective Copy）**：通过辅助模块在推理过程中识别并复制关键上下文 token 到近邻位置，增强模型对重要信息的感知密度。
- **提示压缩（Prompt Compression）**：LLMLingua 等方法使用小型语言模型（GPT2-small 或 LLaMA-7B）识别输入中的冗余 token，实现最高 **20 倍压缩比**，在降低成本的同时保持任务准确率。Selective Context 进一步通过系统化剪枝去除冗余信息。
- **SK 梦境检索（Search Knowledge / Dream Retrieval）**：学术界和工业界正在探索模拟人类在长文本中"跳读-定位-精读"的认知策略，通过学习的跳读策略（Skip）快速扫描全文定位关键段落，再进行深度推理，避免对每个 token 逐一计算注意力。
- **MInference**（微软，2024 年）：通过识别注意力矩阵在长上下文中呈现的三种空间聚合模式——A形（局部聚集）、垂直-斜线（对角线相关）、块稀疏（段落级依赖）——构建动态稀疏索引，在 A100 上实现 Prefill 延迟降低 **最高 10 倍**，且几乎不影响输出准确性。

## 四、真实场景评估方法

### 4.1 Needle in Haystack（大海捞针测试）

大海捞针是评估长上下文能力最直观的测试范式：将一条关键信息（"针"）随机插入长文本（"草垛"）的不同位置，在文本末尾提出与该信息相关的问题。如果模型能准确回答，则认为它成功"从大海中捞起了针"。

标准大海捞针测试通常覆盖以下维度：
- **不同插入位置**：开头 1/4、中间 1/2、末尾 3/4 等，以测试模型对全文本位置的信息保持能力
- **多根针同时插入**：测试模型的多跳推理能力，而非简单的单点检索
- **不同序列长度**：从 4K 逐步扩展到 1M，观察性能衰减曲线
- **噪声文档干扰**：使用真实长文档（如哈利波特书籍、财报文本）而非随机填充

2024 年社区开展的多模型横向评测（总花费约 4300 RMB，覆盖 20+ 模型，每个模型消耗约 3M 输入 token）揭示了几个关键发现：
- GPT-4o-mini 在 128K 长度下正确率稳定保持 **100%**，且性价比最高
- Gemini 1.5 Flash/Pro 在百万 token 级仍保持较高准确率
- Claude 3.5 Sonnet 在复杂推理类大海捞针任务上领先，但 API 有严格的速率限制
- 国内模型（GLM4、DeepSeek、Kimi）在 128K 级基本通过测试，但超过 128K 后性能衰减比海外头部更明显

### 4.2 综合 Benchmark：LongBench

LongBench 是目前最具代表性的长上下文综合评测套件，涵盖六大任务类型：
- **多文档问答**（Multi-Document QA）：跨多个文档的信息整合
- **代码补全**（Code Completion）：长代码文件的上下文理解
- **摘要生成**（Summarization）：超长文本的压缩表达
- **事件时序推理**（Event PII）：长文本中事件的时间顺序理解
- **对话理解**（Dialogue Understanding）：多轮对话的长期依赖
- **刺猬狐狸测试**（Hedgehog/Fox）：需要全文推理的复杂问题

LongBench 的评估长度从 1K 到 20K tokens，能够系统性地刻画模型在不同长度区间的能力差异。

### 5.2 重点深度分析

**DeepSeek 的差异化竞争优势**值得重点关注。DeepSeek-V3 引入的**多头潜在注意力（MLA）**机制，通过低秩联合压缩将每 token 的 KV 缓存从传统 MHA 的数百 KB 压缩至约 **70 KB**。具体做法是：对输入进行下投影（Down-Projection）生成压缩的潜在向量，仅缓存压缩表示，推理时通过上投影（Up-Projection）恢复维度参与注意力计算。在 FP8 混合精度和 MoE 架构的配合下，DeepSeek-V3 激活参数仅 37B（总参数 671B），128K 推理速度提升 **2.3 倍**，内存节省 **60%**，API 价格也极具竞争力。

**百度的明显短板**同样值得关注。尽管百度在 2024 年推出了 ERNIE-Speed-128K 等长上下文版本，在大海捞针测试中有一定改善，但整体而言文心一言在长上下文任务上的表现弱于其他国产头部模型。百度的优势更多集中在中文 NLP 的传统任务（如实体识别、情感分析）而非复杂长文档推理。

**腾讯 Hunyuan 和阶跃星辰 Step** 的 Context Prefix Cache 功能值得关注：在多轮对话或同一文档的重复查询场景中，首次 Prefill 后的 KV 缓存可以被复用，大幅降低重复场景的推理成本。这是一种工程优化，但有效降低了实际使用成本。

**阿里通义千问的特殊情况**：qwen-long 在测试中疑似采用 RAG 方案而非真正的 128K 端到端处理；开源版本 qwen2-72b-instruct 通过 LMDeploy 的 dynamic ntk 配置（session_len=200000, rope_scaling_factor=2.0）可将上下文外推到 200K 长度，在开源社区得到广泛应用。

### 5.3 综合排名

从长上下文能力维度综合排名（2024 年中数据）：
1. **第一梯队**：Anthropic Claude 系列、OpenAI GPT-4o 系列、Google Gemini 系列（海外头部，技术与产品成熟度均领先）
2. **国内较好表现**：智谱 GLM4、DeepSeek、月之暗面 Kimi、阶跃星辰（基本通过 128K 级测试，部分能力接近海外头部）
3. **国内有待提升**：百度 ERNIE（整体不擅长长上下文）、科大讯飞（风控问题影响实际使用）、商汤 SenseChat（风控过严）

## 六、应用场景与成本分析

### 6.1 主要应用场景

长上下文窗口解锁了一系列此前技术上不可行的应用场景：

**科研文献与学术分析。** 一位研究员可以将一个季度内发表的上百篇相关领域论文一次性输入模型，让模型进行跨文献知识整合、研究空白识别和研究假设生成。这在生物医学、材料科学等领域尤为有价值——这些领域的知识高度分散，单篇论文的信息密度有限，全局关联才能产生洞见。

**金融研报与财报解读。** 单篇年报的文本长度通常在 5-15 万字之间，一份招股说明书可达 20 万字以上。长上下文模型可以直接处理整份文档，提取关键财务指标、识别风险条款、发现不同期间报告之间的趋势关联，而无需人工切分和分段处理。

**代码库理解与重构。** 对于大型代码仓库（数千个文件，百万行代码），传统的做法是将单个文件作为上下文单元。长上下文模型使得对整个代码仓库进行架构级分析成为可能：跨文件依赖关系追踪、潜在 bug 的全局影响评估、代码重复与冗余检测等。

**法律合同审查。** 长文本能力让模型可以同时处理数十份合同文档，识别条款之间的潜在冲突、标记异常条款、追踪法律条文的修订历史，辅助律师完成尽职调查中的大量文档审查工作。

**多轮 Agent 系统的状态维护。** 在复杂的 agent 任务（如自动化研究助理、代码开发助手）中，长上下文允许模型在整个任务周期内维护完整的中间状态历史，避免因对话轮次增加导致早期关键信息被截断丢失。

**视频与音频转录分析。** 将长视频的字幕或播客转录文本整体输入，进行深度问答、话题提取和关键信息定位。一个 2 小时播客的转录文本约 2-3 万字，恰好在长上下文的舒适区内。

### 6.2 推理成本的结构性挑战

长上下文的推理成本来自两个主要组成部分：

**KV 缓存的显存占用。** 每个 token 都需要缓存其 Key 和 Value 向量。对于 70B 参数模型使用 BF16 精度，当上下文达到 128K tokens 时，仅 KV 缓存就需要约 16 GB 显存。多用户并发时，这一数字线性叠加，成为部署的主要瓶颈。

**Prefill 阶段的计算成本。** Prefill 是处理输入提示（prompt）并生成首个输出 token 的阶段，其计算量与输入长度的平方成正比（O(n²)）。当输入为 128K tokens 时，Prefill 阶段可能占用整个推理过程的 **50-80%** 时间。

典型成本对比（以 128K token 输入 + 1K token 输出为例）：
- 短上下文（4K）：Prefill 约 0.5 秒，总成本极低
- 中等上下文（32K）：Prefill 约 5-10 秒，成本上升 10 倍
- 长上下文（128K）：Prefill 约 30-60 秒，成本再上升 5-6 倍

### 6.3 成本优化技术生态

**PagedAttention（vLLM）** 是生产环境中最广泛使用的优化技术。其核心思想借鉴操作系统虚拟内存的分页机制，将 KV 缓存分成固定大小的块（block），通过映射表管理逻辑块到物理块的对应关系。这种设计解决了传统方案中的显存碎片化问题，将 GPU 利用率提升 **2-10 倍**，吞吐量和成本效益大幅改善。

**KV 缓存量化。** KVQuant 等工作将 KV 缓存压缩至 2-4 bit，在保持精度的同时将显存占用降低 4-8 倍。结合逐向量（per-vector）的异常值检测，可以在稀疏形式下高效存储高影响力 token 的表示。

**MLA 低秩压缩。** DeepSeek-V3 的 MLA 将每 token KV 缓存从数百 KB 降至约 70 KB（压缩比超过 5 倍），且通过端到端训练保证压缩不损害模型能力。

**前缀缓存复用。** Anthropic 的隐式 Context prefix cache 和腾讯 Hunyuan 的 Context prefix cache 功能，允许同一对话中后续查询复用已 Prefill 的 KV 缓存。这一优化在多轮对话场景下效果尤为显著，可将重复场景的推理成本降低 **80% 以上**。

### 6.4 企业选型决策框架

## 七、技术趋势与未来展望

### 7.1 上下文窗口的持续扩张

Llama 4 Scout 已将开源模型的上下文窗口提升至 10M token 级别。业界共识是：到 2026 年，主流商业模型将普遍支持 **1M+ token** 的上下文窗口，超长上下文将从"黑科技"变为商业模型的标配能力。

### 7.2 稀疏注意力走向原生可训练

NSA 等工作的核心意义在于证明了"稀疏注意力可以端到端训练且不损害能力"。这一范式转变将推动稀疏模式与模型架构的深度融合——未来可能出现"稀疏原生"的模型设计，而非在稠密模型上事后稀疏化。

### 7.3 推理成本持续下降

MLA 压缩、KV 量化、前缀缓存等技术的组合效应，正在将 128K 推理的综合成本拉低到大规模商用的门槛。以 DeepSeek 为代表的"高效率低价格"路线正在重塑行业定价体系，预计 2025 年长上下文的单位 token 成本将比 2024 年下降 **50-70%**。

### 7.4 评估体系走向成熟

大海捞针测试将被 LongBench 等综合 benchmark 补充，评估维度也将从"能否找到"扩展到"能否正确推理"，涵盖多跳推理、跨文档信息聚合、长程逻辑一致性等更复杂的能力维度。

### 7.5 国产模型的追赶路径

DeepSeek-V3、GLM4、Kimi 等在 128K 级已接近海外头部水平，部分指标（如 DeepSeek 的性价比）甚至实现超越。未来竞争的关键战场将在两个方向：一是 **1M+ 超长上下文的稳定性**，二是 **推理成本效率的持续优化**。随着国产模型在工程优化层面的快速迭代，差距正在显著收窄。
